In a mixed project, give independently verifiable work to separate owners when the handoff is worth it. Keep interdependent judgments together and pass agreed findings to downstream work.

## Choose Balance first

1. **Use the same acceptance requirements across presets.** Check any error that can invalidate the deliverable. A missing cost or error measure leaves that comparison open.
2. **Match score, cost and error measures.** Use the closest task-specific benchmark with matching model effort and setup. Compare acceptance-relevant errors alongside quality and cost. Add verification and rework to total cost when measured. Most public benchmarks report execution cost only.
3. **Choose from the measured tradeoffs.** With an average budget, select the highest quality that fits it, breaking ties by lower cost. With a quality target, select the cheapest pair that meets it. When neither is set, report the budget ranges where the measured pairs lead. The preset defaults are recommendations for typical work. Review a conditional alternative when the task changes the cost or the consequences of an error. [Reproduce the budget comparisons](benchmarks/README.md#compare-the-v070-defaults)
4. **Extend from Balance.** Economy buys less quality headroom where the same requirements still hold. Quality and Extra Quality pay progressively more for improvements that matter to the assignment. They can share a pair when the next upgrade adds another material risk or lacks a supported gain.

The AA indexes give weighted scores and costs across a portfolio of tasks. Use their weights and subscores to check task coverage and identify candidates, and use the weighted costs for like-for-like comparisons of the same index. Compare an actual assignment with the most relevant component or dedicated test. The component and its parent index share evidence. ## Two kinds of work with separate defaults

Use **case-specific rule application** when a particular outcome depends on how established rules interact and on the decisive facts. An eligibility decision that turns on how a transition provision changes the applicable requirements qualifies. Applying a complete decision table uses prescribed work. Explaining the provision uses rule interpretation. Establishing a disputed timeline uses heavy evidence synthesis. Choosing a new provision uses design.

Use **constrained model construction** when building or revising an editable model under settled requirements, and checking linked elements across changes determines acceptance. Building a workbook with scenario-linked formulas or revising a CAD assembly can qualify. A fully specified edit or model run with fixed checks uses prescribed work. Use end-to-end tools when choosing tools or assembling the file is the main work. Use code integration when software behavior determines acceptance, and scientific execution when numerical validity does.

The pairs below apply where task evidence is comparable. Otherwise use the general rule-interpretation or end-to-end tools pair, respectively. Each benchmark supports comparisons within its own task setting.
